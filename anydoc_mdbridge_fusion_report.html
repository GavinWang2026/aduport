结论 定义 路线 资产 架构 能力 评分 状态 缺口 合规 风险 路线图
结论先行：按「源码并入、打成一个完整程序」的口径，融合主干已经落地并可运行： native/anydoc/（约 24,361 行 Rust / 76 个 .rs）经 maturin 编为 mdbridge_native._doc；适配层只改 1 处 import；快通道 + DocumentModel 映射 + CI native-build + 前端 12 个新源格式均已接通；上游联网 OCR（ocr="hosted"）在绑定层已裁剪。

综合评分（加权）：融入前 50.8 → 外部 wheel 93.3 → 源码融入现状 94.1 （相对 v1 报告的 96.4，本版因 Docker 未编扩展、仓库双树并存、target/ 构建产物膨胀、.env 缺项等交付洁净度扣分，见 §6 / §8）。 距「产品级完全融入」还差收尾，不差引擎。

1. 「完全融入」的精确定义（BOSS 口径）

是什么

  • anydoc 源码进入 md-bridge 仓库（native/anydoc/）
  • 构建时编成 本程序自己的 原生扩展 mdbridge_native._doc
  • 运行时 不 pip install firecrawl-anydoc
  • 可裁剪（已删联网 OCR）、可演进、可离线构建与分发
  • 对外仍是一个产品：SDK / CLI / API / Web UI 双向转换壳不变

不是什么

  • ❌ 仅依赖 PyPI 的「可选加速器」（路线 A，已否决）
  • ❌ 用 anydoc Document 替换 DocumentModel（会毁掉双向导出）
  • ❌ 引入 Firecrawl hosted OCR（违反私有化零外链）
  • ❌ 并入 Node / WASM / bench / fuzz / Agent Skill（与产品运行时无关）
  • ❌ 让 anydoc 负责 MD→DOCX/PDF 导出（它只做导入侧）
一句话：anydoc = md-bridge 的内置只读解析内核；md-bridge = 双向产品壳 + OCR + 导出器 + 服务化能力。两者合成一个程序，职责不混。

2. 两种集成路线（为何采用源码融入）

维度路线 A：外部 PyPI wheel（否决）路线 B：源码 vendoring 内联（采用）
私有化契合度运行时仍可能外拉 firecrawl-anydoc源码在仓、构建可离线、分发自包含
零外链合规wheel 原样携带 ocr="hosted"vendoring 时裁剪联网分支
程序完整性依赖外部组件，不是「一个程序」Rust 解析器是 native 子组件
可裁剪 / 可演进只能整体接受上游可改源码、改绑定、加自有特性
维护成本跟 PyPI 升级需 sync_anydoc.sh / subtree 同步
构建复杂度pip 一行需 Rust + maturin（已封装 build_native.sh）
许可MITMIT，保留 LICENSE / 版权头即合规
路线 B 以「稍高的构建/同步成本」换「彻底自包含 + 零外链 + 可裁剪」，与禁 GPL、禁外链、禁 LibreOffice 重依赖的硬约束对齐。

4. 融合架构与数据流

md-bridge/                          ← 单一完整程序
├─ native/anydoc/                   ← vendored 解析内核（原 anydoc）
│  ├─ Cargo.toml / src/             ← 24k 行 Rust
│  ├─ python/                       ← PyO3 → mdbridge_native._doc
│  └─ LICENSE
├─ scripts/build_native.sh          ← maturin 离线构建 + 安装
├─ scripts/sync_anydoc.sh           ← 上游半自动同步
├─ backend/app/
│  ├─ importers/anydoc_bridge.py    ← 适配层（import mdbridge_native._doc）
│  ├─ core/registry.py              ← _wire_anydoc（anydoc-first + native-fallback）
│  ├─ core/converter.py             ← MD 快通道 / DocumentModel 慢通道
│  └─ core/document_model.py        ← span / 编号 / 公式 / 脚注
├─ frontend/                        ← SourceFormat 已暴露新格式
└─ .github/workflows/ci.yml         ← native-build 作业
调用链： convert() → 目标=MD 且允许时 _try_anydoc_fast_markdown → mdbridge_native._doc.to_markdown_bytes（零保真损失） → 否则 import_via_anydoc → to_document → 映射 DocumentModel → 既有导出器（docx/pdf/html/epub…）。 可恢复失败降级原生 importer；未编译扩展时 anydoc_available()=False，行为回退旧版。

9. 许可与私有化合规

  • 依赖树：anydoc 传递依赖约 144，核验为零 GPL / AGPL / SSPL（MIT / Apache-2.0 / BSD 等），满足禁传染许可。
  • Vendoring：上游 MIT；保留 native/anydoc/LICENSE 与版权头即合规。
  • 零外链：上游 Python ocr="hosted" 会把文档发往 api.firecrawl.dev——绑定层已删除；扫描 PDF 继续走 md-bridge 本地 OCR（Tesseract / docling / MinerU 等，由配置决定）。
  • 无 LibreOffice：二进制 Office 由纯 Rust 解析，避开 MPL/LGPL 重依赖。
  • 注意：vendored README 文案仍提 hosted OCR，属文档污染，应清理以免审计误判。
