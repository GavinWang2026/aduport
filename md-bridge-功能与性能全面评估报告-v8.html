4.3 逐工具深度剖面

🔵 md-bridge（评估主角）

项结论
独有能力29×18 双向矩阵 + 统一 DocumentModel AST（32 语义节点），批注/修订/透视/文本框/内容控件可穿透到 html/epub/docx/pdf/pptx/xlsx/json；表格 span 共享逻辑覆盖 11 路目标；内置 OCR 双引擎（MinerU/Paddle，可选）、Job+Webhook、多租户 quota、Prometheus 就绪
相对竞品的胜负手可私有化 + 双向 + 服务化一体：docker compose 起一套即得文档交换中台，天然适配企业知识库/合同归档/合规数字化场景
明显短板PDF 语义还原非排版级；docx 深布局强依赖 anydoc（自研 docx_text 覆盖弱）；性能受隔离 fork 开销影响；生态与社区远小于头部竞品（xlsx span 往返已在 v8 闭环）

🔴 anydoc（Firecrawl · Rust）— md-bridge 的「被内化对手」

定位是 「office → LLM-ready Markdown」的单向快通道，不是转换平台。毫秒级、无网络、Rust 内存安全；格式覆盖 doc/ppt/xls(xlsb)/odt/ods/odp/rtf/epub/csv/pdf，含 legacy OLE——这正是 md-bridge 导入矩阵的支柱。多语言绑定（Node/Py/WASM）+ 浏览器 demo。

对比项结论
与 md-bridge 关系md-bridge 已 vendored anydoc 为 mdbridge_native._doc（同 SHA pin）——对手已被收编为引擎层；但单点风险并存：anydoc 上游演进/授权变化直接影响 md-bridge 导入深度
无法替代 md-bridge 的部分anydoc 不做双向（无 md→docx/pdf 等导出）、无 AST 语义（批注/修订/透视）、无服务化/Job/多租户、无 OCR 编排
六维均分结构 8.5 / 整洁 8.5 / 深度 7 —— 库级标杆，但完整性仅 5.5

🟠 mammoth（docx 单项专家）

把 .docx 的语义（Heading 样式/列表/表格/脚注）映射为干净 HTML，风格映射（style map）是核心可扩展点；设计克制：不追求视觉复刻、不做输入消毒、忽略评论/表格格式，README 明确声明 XSS/DoS 风险需隔离运行。有 JS/Python/.NET 多平台实现，6.3K★ 三十年如一日稳定。

对比项结论
长处docx→HTML 语义提取质量高且零依赖重；风格映射 API 优雅
与 md-bridge 关系格式覆盖 1 vs 29，不在同一赛道；md-bridge 的 docx 行内保真仍绑 anydoc，可借鉴 mammoth 的 style-map 思路做自研兜底

🟢 markitdown（微软 · 177.9K★ 的 LLM 转换事实标准）

定位「任意文件 → Markdown 给 LLM 吃」，17.8 万星的社区热度碾压全场。特性：轻量、可选依赖、3rd-party 插件体系、图像走 LLM 描述、音频/YouTube/zip 等新潮格式、可选接 Azure Doc Intelligence/Content Understanding 做云增强（字段级 YAML front-matter 抽取）。官方明说「面向文本分析而非高保真人读转换」。

对比项结论
长处生态与热度、插件化、云增强路径、格式覆盖面（尤其媒体类）
短板单向、无统一语义 AST（表格合并/批注/修订不进 md）、无服务化/Job、深度有限
对 md-bridge 启示LLM 语料方向是 max(热度) 赛道；md-bridge 可用「AST→GFM 快通道」对标其 md 质量，同时守住其不具备的双向+服务化护城河

🟡 unstructured（RAG ETL 管线）

面向「解析→分区→清洗→分块→嵌入」RAG 全链路，核心是带元数据的 elements 模型；hi_res 模式用深度学习布局模型 + OCR 提表格结构。Docker/MCP Server/无服务器 API 都有。注意：仅 Python 3.12、依赖重（libmagic/poppler/tesseract/libreoffice/pypandoc）、默认遥测（可关）、CJK 分组有已知缺陷。

对比项结论
与 md-bridge 关系互补 > 竞争：unstructured 是「解析到向量库」的 ETL 中间层；md-bridge 是「格式间交换」的中台。若 md-bridge 要进入 RAG 市场，可输出 docling/unstructured 风格的 chunk/element 契约，而非自研全套

🟣 docling（IBM · 65.9K★，AI 版面理解标杆）

把 PDF/Office/网页/图片经 AI 版面分析 + 表格结构识别读入统一 DoclingDocument（与 md-bridge 的 DocumentModel 理念同构），导出 md/html/JSON；支持 EPUB/ODF/Apple Pages/邮件/音视频等 15+ 输入；离线模型 + VLM 可选。被 IBM 捐赠 LF AI & Data，版本迭代极快（2.124）。

对比项结论
理念对标DoclingDocument ≈ DocumentModel——但 docling 的 AI 版面/表格模型让 PDF 深度更强；md-bridge 的 AST 节点面（批注/修订/透视/内容控件）更贴 office 语义
对 md-bridge 启示md-bridge 已将其列为可选 importer（[office] extra + PDF 引擎之一）——正确策略：深度引擎外包，AST 归一自持；应把 docling 输出充分映射进 32 节点，补 PDF 版面短板

🟤 pandoc（46.1K★ · GPL-2 的瑞士军刀）

40+ 格式转换的事实标准，Haskell 强类型、reader/writer 分离 + 通用 AST + Lua filter 可编程；引文/参考文献体系独步。边界：office 双向弱（docx/odt 仅读写，pptx 只出不进，xlsx 靠 csv 表格）、PDF 需外挂引擎、无服务化。GPL-2 意味着 md-bridge 不能打包分发（其 README 已注明此边界）。

对比项结论
格式广度 vs md-bridgepandoc 在标记语言族（rst/org/mediawiki/texinfo/jats…）广度碾压；md-bridge 在二进制 office/ebook 族（doc/ppt/xls/pptx/xlsx/epub/mobi/azw3/kf8）更实用——两条赛道互补
许可影响md-bridge 可调用 pandoc（子进程/可选），但不可静态打包进 MIT 发行物——这与禁止打包 LibreOffice 同理

⚪ LibreOffice（headless · 排版级保真之王）

soffice --headless --convert-to 是自托管文档转换的「workhorse」：读写微软格式、ODF、CSV/HTML/RTF/PDF，像素级排版保真（字体/页边距/分页），适合 docx→pdf/xlsx→pdf 等「要长得像」的场景。代价：进程重（2–3s 起）、无语义 AST（批注/修订要抠内部 XML）、并发需独立 profile、依赖字体环境。

对比项结论
与 md-bridge 关系理想补充而非对手：md-bridge 的语义 AST 负责「数据/结构正确」，LibreOffice（若引入）负责「排版级 PDF/office 复刻」。但体积与许可（MPL/LGPL，可调用不可内嵌发行策略）需评估——当前 md-bridge 明确不打包

06竞品格局下的战略定位

结论先行：md-bridge 不该去和 markitdown/docling 抢「单文件 → LLM 文本」的库赛道，而应坐实「可私有化部署的双向文档交换中台」——这是七工具中唯一无人占据的位置：anydoc/mammoth/markitdown/docling 是单向引擎，pandoc 是单机 CLI，LibreOffice 是排版套件，只有 md-bridge 提供 AST 归一 + 双向转换 + 服务化的一体化产品。
护城河（保持）补短板（对齐竞品）差异化卖点（对外）
29×18 双向矩阵 · 32 节点 AST · 安全硬门禁 · Job/多租户服务化 · OCR 可选xlsx span 往返 · docx 自研深度 · PDF AI 版面 · 性能曲线公开 · 社区样板案例「一个私有化网关，Office/PDF/电子书/表格双向互转，语义不丢，数据不出内网」
