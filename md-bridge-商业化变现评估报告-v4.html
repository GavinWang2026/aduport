1.2 三个必须立刻知道的判断

  1. PDF 是这门生意的主战场，而它现在是坏的。PDF⇄Markdown 是文档转换最高频、最愿意付费的场景 （RAG 知识库、合同解析、报告生成）。但实测：导出中文变 ??????，导入每个文件卡 150 秒且内容大量丢失。 P0 不修，任何变现动作都是零。
  2. MIT 协议决定了「卖软件」不成立，「卖省心」才成立。核心代码 MIT 开源，任何人都能免费自托管。 唯一卖点是：客户不想自己装 Pango、不想下 3GB docling 模型、不想调中文排版。 所以定价锚点是「省下的运维时间」，不是「功能数量」。
  3. 快速变现的正确顺序是 B→A，不是 A→B。先做 SaaS 需要 6–8 周建多租户+计量+支付+订阅， 现金流在第 9 周；先做企业私有化交付只需 2 周（修 P0 + 打包离线模型 + SLA 模板）， 第 14 天就能开票。用 B 的现金流养 A 的建设。
给 BOSS 的一句话建议：不要现在投 SaaS。用 2 周修掉 PDF 两项 P0（第 3 项多租户仅 SaaS 需要，可延后）、把 docling 模型和中文排版预置进交付包， 先以「企业私有化文档转换中台」的形态拿下 2–3 个 ¥15,000–50,000 的单子；拿到现金流后， 再用 6 周建 SaaS 基建做规模化。这条路 90 天内能看到真金白银，另一条路 90 天可能还在调 Stripe Webhook。

3 · P0 致命缺陷：中文 PDF 全损 + 150 秒阻塞P0 Critical Defects

以下三项不是「建议优化」，是「不修就不能卖」。全部集中在 PDF 链路—— 而 PDF 恰好是文档转换领域付费意愿最高、客单价最高的场景。所有结论均由本机实测得出，非静态推断。

3.1 已修复 P0-1 PDF 导出中文全部渲染为问号 —— 输出 100% 不可用

复现过程

# 输入
MD = "# 中文标题测试\n\n这是中文段落内容。\n"
out = convert(MD.encode('utf-8'), 'md', 'pdf', filename='d.md')

# 实测结果
SIZE: 603 bytes
Fonts: [b'Helvetica']        ← 无 CJK 字体，无 /Encoding
Stream: BT /F1 11 Tf 14 TL 50 750 Td (# ??????) Tj
        T* (?????????) Tj ET
CJK_IN_STREAM: False

中文全部丢失，变成 ASCII 问号。对一个中文市场产品，这意味着 PDF 导出功能等于不存在。

根因

macOS（以及一切缺少 Pango/GObject 的环境）下 WeasyPrint 无法初始化， pdf_exporter 静默降级到 pdf_simple（backend/app/exporters/pdf_simple.py）。 该降级实现用 Helvetica + WinAnsiEncoding 直接写 Tj 字符串， 既不嵌入 CJK 字体，也没有 ToUnicode 映射，更没有把中文转成 CID 字形—— 任何非 Latin-1 字符在编码阶段就被吞掉。

商业影响

影响面后果
目标客户中文企业客户 100% 无法使用 PDF 导出，而这是最高频需求（报告、合同、归档）
SaaS 转化免费用户首次试用即产出废文件，转化率断崖；且失败是静默的——用户拿到的是「成功」的 PDF
口碑风险静默降级比报错更危险，客户在正式场合发现文件是乱码，信任直接归零

修复方案（3 选 1，推荐 A）

方案做法工作量评价
A pdf_simple 内嵌 CJK 子集字体：改用 Tj → Identity-H 编码 + 嵌入 Noto Sans SC 子集（可用 fonttools 做子集化），并写 ToUnicode CMap 2 人日 已落地 Identity-H + 子集字体 + ToUnicode（2026-08-31）
B Docker 镜像强制装 Pango，把 WeasyPrint 变为硬依赖，移除 pdf_simple 降级路径 1 人日 镜像体积 +180MB，且丧失 macOS 本地可用性
C 降级时返回 422 明确报错，不产出损坏文件 0.5 人日 仅止血 必须做，但不能替代 A/B

建议：C 立即上线（止血，0.5 人日）+ A 两周内完成（根治，2 人日）。

3.2 已修复 P0-2 PDF 导入每个新文件阻塞 150 秒，且内容大量丢失

复现过程（三个内容互不相同的 PDF，确保缓存未命中）

# 环境：docling 已安装，但模型未预下载
$ ls ~/.cache/docling/models  → No such file or directory
docling_artifacts_path = ''   hf_endpoint = ''

pdf#0 (unique content):  160015.8 ms  out=35B  text='# d0\n\n# ??0 ?0????????????????????'
pdf#1 (unique content):  150358.2 ms  out=35B  text='# d1\n\n# ??1 ?1????????????????????'
pdf#2 (unique content):  150262.4 ms  out=35B  text='# d2\n\n# ??2 ?2????????????????????'

三个文件、每个 150 秒、每个只还原 35 字节、中文全是问号。「首次冷启动慢」的假设被证伪—— 这是每个文件的稳定表现。

根因链

  1. pdf_importer.import_pdf 优先走 docling（_import_with_docling）
  2. docling 构造 DocumentConverter 时需要 layout / tableformer 模型
  3. 模型不在本地 → 尝试从 HuggingFace Hub 下载 → ConnectTimeout（国内网络直连 HF 基本必然超时）
  4. 超时耗时约 150 秒（TCP 重试 + 退避），期间请求线程完全阻塞
  5. 捕获 _is_hub_network_error 后降级到 pdf_text_fallback 文本层提取
  6. 文本层提取同样丢中文（只还原 35 字节），且无表格/标题结构

关键放大因素：同一 PDF 第二次转换仅 0.3ms —— 但那是 result_cache 命中， 不是 docling 变快了。缓存掩盖了问题，让开发者误以为「只是首次慢」。 一旦上线，每个用户的每个新 PDF 都会踩一次 150 秒。

商业影响

  • SaaS 场景直接判死：任何 HTTP 请求阻塞 150 秒都会先被网关 / 客户端 / 负载均衡超时断开（通常 30–60s）， 用户看到的是「504」而不是「转完了」
  • 成本失控：一个 Worker 被单文件占用 150 秒，batch_workers=3 意味着 3 个并发就能让整个实例停摆 2.5 分钟 —— 这是极低成本的 DoS 攻击面
  • 企业交付场景：内网客户无外网，100% 触发此路径，POC 现场直接翻车

修复方案

#动作工作量效果
1 构建期预下载模型：scripts/download_docling_models.sh 已在仓库中， 在 Dockerfile 里执行并 bake 进镜像（配 HF_ENDPOINT=hf-mirror.com） 1 人日消除运行时联网，首次耗时 → 模型加载约 3–8s
2 设置模型缺失快速失败：启动时探测模型目录，不存在则直接关闭 docling 路径 （不再尝试联网），默认走文本层 0.5 人日150s → <100ms
3 给 docling 调用加显式 timeout 参数 + 全局转换超时熔断 0.5 人日兜底，避免任何路径无限阻塞
4 默认关闭 OCR（ocr_enabled），改为按需显式开启（RapidOCR 首次初始化也在加载模型） 0.25 人日降低冷启动与内存占用

app/api/auth.py 中，鉴权只比对一个全局字符串：

6.3 为什么企业私有化交付是「最快」的（详细论证）

① 绕开全部计费基建

企业客户走合同 + 对公转账 + 发票， 不需要 Stripe、不需要订阅系统、不需要用量计量。 SaaS 那 19 人日的基建，企业交付一分钱都不用花。

② 缺陷变成卖点

「docling 模型 3GB 难下载、Pango 依赖难装、中文排版难调」—— 对 SaaS 是缺陷，对企业交付恰恰是付费理由： 客户不想自己解决这些，你打包好交付给他们，价值感极强。

③ MIT 不冲突

客户买的不是代码（代码 MIT 免费）， 买的是「部署好的系统 + 运维责任 + SLA 承诺 + 中文质量兜底」。 这在法理和商务上都站得住，不会引发「为什么不直接用开源版」的质疑。

企业版「离线交付包」应包含什么（这是你真正的商品）：
  1. Docker 镜像（docling 模型已 bake，约 3GB，内网可直接 docker load）
  2. CJK 字体包 + PDF 中文排版配置（解决 P0-1）
  3. 一键部署脚本（./install.sh）+ 离线文档（PDF/HTML）
  4. License Key 校验模块（离线激活，按机器指纹 / 到期时间）
  5. SLA 模板 + 商业授权书 + 运维手册
  6. 3 个月免费维护 + 后续 ¥8,000/年

9 · 竞品对标与差异化护城河Competitive Landscape

文档转换是红海，但「中文场景 + 私有化 + 全格式」这个交集里，玩家很少。

9.1 竞品对比矩阵

竞品协议格式覆盖 中文 PDFmd-bridge 的相对位置
PandocGPL-2极广（40+）依赖 LaTeX md-bridge 明令禁止打包 Pandoc（GPL 污染）。差距：格式广度。 优势：MIT 可商用、无需 LaTeX 环境
CloudConvert商业 SaaS极广（200+）良好 它是 md-bridge SaaS 路线的直接对手。 差异化：私有化部署 + 数据不出内网 + 国内支付
Zamzar / Convertio商业 SaaS广一般 同上，且中文排版较弱。差异化：中文排版质量 + API 友好度
docling（IBM）MIT聚焦 PDF 解析需自行配置 md-bridge 已作为内置引擎使用。 关系：依赖而非竞争，但需解决其模型分发问题
MinerUAGPL-3PDF → MD优秀 中文 PDF 解析的强力对手，但 AGPL 协议对商业闭源极不友好 —— 这正是 md-bridge 的机会窗口
Marker / NougatMIT / ApachePDF → MD（学术）弱 偏英文学术论文，中文支持弱。md-bridge 中文场景占优

9.2 护城河分析：什么能守住，什么守不住

✗ 守不住的（不要押注）

  • 格式数量 —— CloudConvert 支持 200+，你永远追不上
  • 转换速度 —— 纯 CPU 任务，没有结构性优势
  • 代码本身 —— MIT 开源，任何人可自托管
  • 价格战 —— 大厂可以免费，你打不起

✓ 守得住的（重点投入）

  • 私有化交付能力 —— SaaS 竞品天然做不了内网交付
  • MIT 协议洁净度 —— 对标 MinerU 的 AGPL 与 Pandoc 的 GPL， 这是企业法务评审的硬指标
  • 中文排版质量 —— 英文系工具普遍做不好 CJK， 修复 P0-1 后这是真实壁垒
  • 离线可用 —— 无外网环境（政务、军工、内网）刚需
  • 本地客户关系与服务 —— 响应快、可定制、可上门
最重要的战略判断：md-bridge 的最大资产不是 210 个格式组合， 而是「MIT 洁净协议 + 可完全私有化」这个组合。 中文 PDF 解析做得最好的 MinerU 是 AGPL-3——企业一旦使用就面临开源传染风险， 法务基本会否掉。把「协议洁净」做成营销卖点，比多做 20 个格式更有商业价值。

10.2 如果只做一件事

修 PDF 中文（P0-1 + P0-2，4.25 人日）

如果 BOSS 只能批一件事的资源，就批这个。理由：

  • PDF 是文档转换付费意愿最高的场景，其他格式（txt/csv/json）用户不会为此付钱
  • 当前 PDF 链路中文 100% 损坏 + 150 秒阻塞，等于这个最高价值的场景完全关闭
  • 4.25 人日 unlock 整个 PDF 市场，是全报告性价比最高的单项投入
  • 不修的话，无论走 SaaS 还是企业交付，客户第一次试用就会翻车

10.3 风险提示

风险概率影响与应对
docling 模型体积高 镜像将达 3–5GB，内网交付需要物理介质或内网镜像仓库。 应对：提供「精简版」（不含 docling，仅 MD/DOCX/HTML 路径）作为备选
MIT 被白嫖高 客户拿了开源版自己部署。应对：不靠代码收费，靠交付与 SLA 收费； 核心增强（CJK 排版、批量引擎、管理面板）可放企业版不开源
PDF 修复难度超预期中 CJK 字体嵌入涉及 PDF 规范细节。应对：先做方案 C 止血， 方案 A 若超期可临时用方案 B（强制 Pango）过渡
企业销售周期长中 大企业采购流程 3–6 个月。应对：优先打中型企业与律所（决策链短）， 或先做 POC 付费试点（¥5,000–10,000）降低决策门槛
